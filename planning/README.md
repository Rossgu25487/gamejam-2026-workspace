## 1. 接收原件

planner 或其 Codex 将适合公开的策划原件复制到 [inbox](inbox/README.md)，也可通过 GitHub 上传到该目录。Godot 日常入口已不提供导入或设当前操作。
保留原始字节、格式与来源；文件重名时使用可区分名称，避免覆盖。收件区已在 `.gitattributes` 关闭文本换行转换，以保持哈希一致。
上传只表示入库，不自动确立当前依据。用户要求修订时保留原件，在 planning 建立清楚版本的工作稿；确认的新版本再独立入库。
私密资料留在仓库外，不因可以上传而公开。读取或格式工具缺失时标明限制，继续可完成部分。

## 2. 明确设为当前依据

只有 planner 明确指定采用的文件和版本后，才由 planner/Codex 更新 [current.json](current.json)。

1. 重新读取现有指针和选中文件，确认原件仍是本次采用的内容，计算实际 SHA-256。
2. 沿现有结构填写 `status: active`、相对仓库根的 `path`（须在 planning/inbox 内）、`title`、`sha256`、`updated_at`；递增本分支的 `revision`。
3. 尚未指定时保留 pending 与空路径/哈希。revision 仅为分支局部计次，任务应引用提交号、策划路径和 sha256，并注明需求 ID。
4. 保存前若发现指针或原件已经变化，先比较并由 planner 核对，不覆盖更新或沿用旧哈希。
5. 将原件、指针与相关需求通过 Git 同步，并在受影响 Issue 更新依据链接和执行验收。其他成员正常同步后再检查直接影响。

原件哈希不匹配时，只把相关依据标待核；不修改原件来凑哈希，也不停止其他独立准备。

策划稿中的设计和验收描述作为来源；执行任务的验收条目、负责人、状态及实际结果统一在 Issue 维护。需要改变规则时先明确规则依据，再同步对应 Issue，不在 handoff 维护第二套清单。
本仓库练习数值为 `game/data/demo_config.tres`，由 planner 修改；类型定义 `demo_config.gd` 归 lead。
handoff 只留任务链接和本机工作稿、分支、未提交文件等恢复线索，公开交接成果放在 Issue 引用的位置。
