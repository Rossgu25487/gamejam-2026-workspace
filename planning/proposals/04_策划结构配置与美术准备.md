# 04｜策划案、配置表与美术准备

2026-09-24。[玩法说明](02_Demo元素与玩家体验.md)｜[制作安排](03_工作计划与关卡推演.md)

## 一、策划案怎样交给团队

四份预研分别解决选什么方向、玩家怎样玩、怎样制作和怎样交接。命题公布以后，正式策划案围绕同一段游玩流程整理，保留以下内容：

1. **概述与范围。** 说明游戏面向谁、主要做什么、目标平台、本版完成哪些内容；附一段从接待到交付的完整例子。
2. **检查与诊断。** 写清玩家能看见的症状、检查工具、反馈、判断依据与提示，避免只留下一个“正确答案”字段。
3. **修补与用途。** 说明各方案保留和失去的功能、顾客是否接受、消耗与施工结果。方案被拒绝和资源不足的原因要能在界面读到。
4. **段落、人物与剧情。** 列出委托顺序、每段新增要求、人物已经知道的事情和回访条件。台词与触发关系相邻，便于程序接入。
5. **界面和资源。** 界面图说明位置，正文补充点击、显示和返回；资源清单区分新图、差分和复用，不用一个“收音机”代替全部状态。
6. **配置与接口。** 指定哪份数据是当前值，谁负责读取、修改和验证。运行状态单独保存。
7. **验收与安排。** 给出能完整走通的例子、容易出错的操作，以及与版本一致的任务和交接时间。

小项目先维护一份总案。只有某部分已长到妨碍阅读，才拆成子文档。配置不重复解释设计理由，测试记录也不另写一套规则。

## 二、配置先服务于一次实际处理

以公共收音机为例：玩家已经判断是发声模块故障，可以提出更换模块或改为耳机输出。前者消耗模块1、工作格1；后者消耗工作格2，失去外放，需要管理员同意听写并转告。只有顾客接受、资源足够且玩家确认施工，才扣除资源并改变设备状态。

因此，配置至少要表达委托、测试现象、故障、方案、用途回应与消耗。钱、采购、日结已经退出推荐玩法，旧版相关字段一并移除。

[候选配置样例](fixtures/修补铺候选配置.json)只用于题前核对，不由当前 Godot 工程加载。资源键是接入时使用的名称，尚未绑定正式图片和声音。样例结构版本为2，与旧经营样例区分。

[配置检查脚本](fixtures/检查候选配置.mjs)可通过 Node 运行，核对ID引用、消耗和最终两条分配算式。它不检查实际游戏的按钮、声音或画面，接入后仍需相应运行验证。

### 2.1 文件结构

| 数据 | 保存内容 | 主要引用关系 |
|---|---|---|
| settings | 结构版本之外的共同行为约定、资源单位 | work为工作格，module为替换模块 |
| tools | 工具名称与用途提示 | 委托的observations以工具ID为键 |
| diagnoses | 故障名称、帮助说明 | case.diagnosis引用故障ID |
| methods | 修补名称、适用故障、消耗、施工后状态 | case.plans引用方法ID |
| cases | 物件、主人、症状、测试反馈、诊断和具体方案回应 | 章节列出case ID；方案引用方法和同意条件 |
| chapters | 本段资源与委托、完成要求、能否重新安排 | 引用case ID，决定本段能做什么 |
| agreements、transfer | 人物对功能变化的同意、一次模块转用 | 施工或转用读取同意标记；转用关联私人收音机 |

ID使用稳定英文标识，展示名称可以修改。数量使用整数，工作量单位为“格”，模块单位为“块”。必填字段缺失、引用不存在或消耗为负时，在载入检查中指出具体记录；文案空白与数值0分别处理。

### 2.2 委托与方案

| 字段 | 类型与含义 | 样例或规则 |
|---|---|---|
| cases.id | string，主键 | c04_public_radio |
| item_key、owner_id | string，物件资源键与人物ID | public_radio、zhou；同一结构可共用美术 |
| title、symptom、need | string，标题、已知症状和使用需要 | “公共收音机”“通电后没有声音”“住户及时收到通知” |
| observations | object，工具ID→检查结果 | contact_test显示接点稳定，speaker_test显示模块无反应 |
| diagnosis | string，引用diagnoses.id | speaker_fault |
| plans | array，本委托允许提出的方案 | 每项包含method_id、accepted、reason、requires_agreement与response |
| plans.accepted | boolean，是否能满足该顾客用途 | 闹钟的耳机方案为false；提出时显示reason，不扣资源 |
| plans.requires_agreement | string或null，必要同意ID | public_manual_notice；未取得时先显示协商内容 |
| methods.cost | object，消耗数量 | {"work":2,"module":0}；资源缺省键按0处理 |
| methods.result_state | string，施工后表现状态 | original、headphones或reconnected |

是否接受保存在本次委托里，不能写成“耳机方案永远有效”或“永远无效”。相同技术处理放到不同使用者身上，可以产生不同答案。首版只需要有限的预设回应，暂不制作任意条件表达式或自由对话判断。

### 2.3 段落与一次转用

| 字段 | 含义与限制 |
|---|---|
| chapters.id、case_ids | 段落主键与本段委托；每件委托只列入一段 |
| chapters.resources | 进入本段后设置的工作格与模块数；前段余量不累加 |
| chapters.must_complete | 教学段需完成全部委托；最终段允许确认留下未处理委托 |
| chapters.allow_replan | 最终段允许恢复本段开始时的状态 |
| agreements.id、owner_id、request、reply | 同意记录的主键、作出同意的人、询问和明确回应 |
| transfer.chapter_id、source_case_id | 转用只在最终段开放，来源是第一段已经修好的私人收音机 |
| transfer.agreement_id、cost、gain | 需要阿程同意；消耗work1，获得module1 |
| transfer.result_state、limit | 来源物件变为headphones；整段限一次 |

进入最终段时，先保存一次完整起点，再允许操作。【重新安排】恢复这一份起点，不能再次叠加供给，也不能保留转用产生的模块。第一次修好过的私人收音机仍是同一个物件，转用后要更新它在柜台和回访中的状态。

### 2.4 配置与运行状态

配置保存规则和内容；一局运行状态保存当前段落、资源、已做检查、诊断结果、委托状态、已取得同意、转用次数与物件表现。界面临时选中的工具和方案另外保存，切换委托时不改变真实资源。

当玩家点击【开始修补】，逻辑重新检查诊断、方案是否接受、同意条件与剩余资源。全部满足后，同一次处理内扣除消耗、记录施工结果、标记委托完成，再通知界面。再次点击已完成委托，只能查看结果，不会再扣一次材料。

Godot的Resource可以保存编辑器中的数据，同一路径的资源也可能被共享。若正式实现采用Resource，需要将只读配置和一局可变状态分开；采用JSON同样需要这一处理。[Godot Resources](https://docs.godotengine.org/en/4.7/tutorials/scripting/resources.html)

## 三、程序之间怎样交接

副程序A负责唯一的规则状态：检查结果、判断、方案条件、资源消耗和段落恢复。副程序B负责物件、文本、控件与差分显示，向逻辑提交操作。主程序负责数据读取、主入口、场景接线、合并与完整包。

交接先用一件委托。主程序载入配置，副程序A能返回状态与操作结果，副程序B用占位图显示并真实点击。三人共同跑完以后，再增加余下委托。主程序无须先造一套可支持所有经营游戏的框架。

最小请求可以是检查工具、提交诊断、提出方案、记录同意、确认施工、转用模块、结束段落、重新安排。响应包含成功与否、原因、当前状态，以及本次需要显示的短反馈。函数名由主程序按实现统一；需求说明以本稿的业务含义为准。

配置变更由策划提交，主程序先检查引用与资源数量，再交给逻辑和界面。文字、状态和图片都使用同一组委托ID，避免程序按名称猜是哪件设备。

## 四、美术先确定哪些事情

### 4.1 画面主次

默认先试低饱和的纸片插画：木柜台、灰绿远景与局部暖光保持统一，物件轮廓比背景细节更清楚。人物采用静态半身，身份通过姿态、服装使用痕迹与携带物区分，表情变化只做确实需要的部分。

![三种画法对照](figures/美术方向对照.png)

左图的手绘纸感更适合旧物叙事，但现有纹理仍偏细；中图的硬边套色更容易控制数量与一致性；右图提供像素方向的参照，尚未通过统一像素网格检查。三列只供选方向，不能直接作为分层运行资源。

REPLACED的参考价值在空间层次。远景压低对比，工具和物件留在清楚的中景，门框或货架作为两侧前景。先用分层素材完成深度感，实时焦点、复杂灯光和角色逐帧动画不进入首版。

### 4.2 一件物品需要交什么

以收音机为例，一张精美概念图还不足以接入。美术B需要在同一画布上保留机壳、刻度、接点、发声模块等必要分层；随后导出正常、检查高亮、已修好、耳机输出几种实际使用状态。它们共用物件位置和主要轮廓，程序只替换或显隐对应部分。

美术A负责委托卡、检查记录、方案卡和确认状态。数字、故障文字和按钮保持原生文本，不能烘焙进背景。深色场景可以保留气氛，长文字仍需稳定的阅读底色。

参考窗口先沿用工程的1152×720。首次样例正文从22px左右开始，标题约30px，辅助说明尽量不低于18px；最终以真实运行尺寸检查。使用色板时先控制明暗和焦点，颜色还需有文字或图形配合，不能只靠红绿区分正确与错误。

源文件保留分层，导出PNG保留透明背景。Krita的图层与蒙版可以用于分离物件和限制局部修改；生成的平面图需要实际拆分或重绘以后，才能按分层源稿交接。[Krita图层与蒙版](https://docs.krita.org/en/reference_manual/layers_and_masks.html)

### 4.3 先用一次样例校准制作速度

两位美术各留60—90分钟，使用已经熟悉的工具。美术A完成一张委托卡和方案按钮的基本状态；美术B完成一件中性旧物的基础图与一个局部变化。把两者放进同一画面，检查物件是否跳位、文字是否被纹理干扰、变化是否看得出。

随后由副程序B接入。能在源稿里修改一个部件、重新导出，并在游戏里正确替换，才说明这条制作方法可以继续使用。若这一轮已经消耗过多时间，就减少纹理或改用硬边套色，再做同一项检查。

## 五、给美术AI agent的固定资料

这里采用固定参考和反复校准的方式：每次任务都读取同一份说明、同一件合格样例和本次要改的部分。普通对话不会自动训练模型权重，跨任务也需要重新提供这些依据。

共同资料入口为[美术参考与提示词](../art-reference/README.md)。它保存本次方向图、实际生成提示词、画布与图层约定，以及认可样例的登记方式。当前方向图只被用作比较，尚没有成员完成并认可的运行资源。

美术A可以把以下任务直接交给自己的agent：

```text
读取项目AGENTS.md、04的美术说明和planning/art-reference/README.md，检查本人分支与已有文件。完成一张中性委托卡：物件名、两行症状、使用需要、已看检查记录、两个方案按钮。按1152×720参考画面保留原生文字，提供默认、选中、不可执行及原因提示。用现有工具保存可编辑源稿，导出必要预览，再配合副程序B检查实际字号和状态。不要扩成整套菜单；记录实际耗时、需要调整的一处问题和交接位置。
```

美术B可以使用以下任务：

```text
读取项目AGENTS.md、04的美术说明和planning/art-reference/README.md，检查本人分支与已有源稿。用默认纸片插画方向制作一件中性收音机：基础图、接点高亮、修好、耳机输出四个状态。保持画布、位置、光向和轮廓一致，必要部件单独分层。若使用图像生成，保留完整提示词、输入参考、工具与人工修改记录；平面PNG如实标为平面图。先完成一件的替换试验，再按实际时间决定是否继续此精度。
```

实际交接写清资源ID、源文件、导出、尺寸、锚点、状态、用途、来源及接收者即可。测试图与正式资源分开；字体、参考图和音效的使用条件随对应资源保留。赛前材料能否进入参赛包，继续由运营核对赛事要求。

## 六、接入前怎样检查

用同一条委托对照正文、配置和界面：测试结果能否支持诊断，方案是否符合顾客需要，消耗是否与剩余资源相符，施工后状态能否找到对应资源。再走一条被拒绝的方案和一次资源不足，确认它们不会扣除资源。

最终段分别验证保留私人设备和授权转用两条路线。重新安排后，已经做过的施工、同意和转用都应回到段落起点。程序验证规则，策划验证解释与人物反应，独立测试验证真实输入和完整包，彼此不能替代。
