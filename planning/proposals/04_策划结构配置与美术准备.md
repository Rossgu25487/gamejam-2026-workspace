# 04｜策划案、配置表与美术准备

2026-09-24　题前候选稿。[玩法说明](02_Demo元素与玩家体验.md)｜[制作安排](03_工作计划与关卡推演.md)

## 一、策划案怎样交给团队

四份预研分别说明选什么方向、玩家怎样玩、怎样制作和怎样交接。命题公布以后，正式策划案围绕同一段游玩流程整理，保留以下内容：

1. **概述与范围。** 说明游戏面向谁、主要做什么、目标平台和本版内容，附一段从接待到交付的完整例子。
2. **物件与试修。** 写清原来的现象、可以临时处理的部位、试听结果和提示。前两段通过试修后的改善开放施工，不设置故障选择题。
3. **用途与方案。** 顾客入场先说生活情境，玩家通过询问取得用途记录；方案说明保留和失去的功能、顾客是否接受、消耗与结果。
4. **段落与人物。** 列出委托顺序、供给、人物已经知道的事，以及同意和回访的条件。台词紧跟触发它的动作。
5. **界面与资源。** 界面图说明位置，正文补充点击、显示和返回。物件基础图、局部差分、声音和文字分别交接。
6. **配置与接口。** 说明每组字段由谁填写、何时读取、怎样产生结果，运行状态单独保存。
7. **检查与安排。** 给出两条完整处理、被拒绝的方案与重新安排的例子，制作工时继续按每人最多24小时控制。

小项目先维护一份总案。配置保存当前取值，正文解释动作和结果；同一规则修改后，对应样例一起更新。

## 二、配置先服务于一次实际处理

第一段开始时，玩家有1格工作量、0块外放模块。阿程的私人收音机声音断续，入场对白只说明这件事；玩家点击【谁来用】【怎样用】，得知他和孩子在家一起听转播，这两项记录留在委托旁。

玩家先接入工具中的检测模块，再点击【试听】，声音仍会中断；改为临时固定接点后再次试听，声音恢复稳定。两次临时处理都不扣资源，也不改变物件的正式状态。至少一次试听确认改善以后，玩家可以预览【重新接好】；确认施工才扣1格工作量，并把同一台收音机记为已修好。

这里的**外放模块仅指外放功放板**。耳机和外放分为两路，取走外放模块会失去外放，耳机通路仍可保留。检测模块属于工具，用完收回，不进入库存。私人收音机原本有耳机口，公共机需要改接接口，这也是转用占1格、耳机改装占2格的依据。

[候选配置](fixtures/修补铺候选配置.json)的结构版本为3，只供题前讨论和数据核对，尚未由Godot工程加载。[检查脚本](fixtures/检查候选配置.mjs)按这份数据推演试修、询问、同意、施工与重新安排；它检查的是设计数据，图片、声音、实际点击和玩家理解还需在可玩版本中验证。

### 2.1 文件结构

| 数据 | 保存内容 | 引用和用途 |
|---|---|---|
| schema_version、status | 结构版本与候选身份 | 本例为3、candidate_pretheme |
| settings | 资源名称、单位、人物名称及资源接入状态 | work为工作量，module为外放模块；资源尚未绑定时为unbound |
| questions | 两项固定询问 | who＝谁来用，how＝怎样用；各委托分别填写回答 |
| trials | 两种免费临时处理 | contact_trial临时接好接点；module_trial接入检测模块 |
| items | 物件名、画面键、共用轮廓与现成耳机口 | 私人、公共收音机共用radio轮廓，标签和接口不同 |
| presentation | 画面状态、声音键与同义文字反馈 | 委托、试听、施工和转用引用同一组表现ID |
| methods | 正式修补操作、消耗、保留和失去的功能 | 委托的plans引用method_id |
| cases | 入场情境、用途回答、临时处理结果、提示和方案回应 | 章节通过case ID确定本段委托 |
| chapters | 本段资源、委托、完成要求和重排入口 | 前段剩余工作格和模块不累加 |
| agreements、transfer | 两项具体同意与一次转用 | 公共机人工转告同意；私人机耳机测试后的主人同意 |
| followup | 设备去向、人工转告、公共时段和未处理委托的回访内容 | 按本次实际施工、转用与未处理结果选择对应文字 |

ID使用稳定英文标识，显示名称可修改。数量为非负整数，单位为“格”或“块”；每组消耗、供给和所得都完整填写work与module，未使用的资源填0。必填缺失、ID重复、引用不存在或数值不合范围时，检查脚本直接指出记录，不补成另一套规则。

### 2.2 顾客、试修与方案

| 字段 | 类型与含义 | 样例或读取方式 |
|---|---|---|
| cases.id、item_key、owner_id | string，委托、物件和主人 | c04_public_radio、public_radio、zhou |
| entry_text、symptom | string，入场情境与物件现象 | 入场先说“通知要送到各房”，用途由后续询问取得 |
| questions.who／how.reply | string，点击相应询问后显示的顾客回答 | 两项询问免费，可重新查看 |
| questions.who／how.record | string，回答后留在界面的用途记录 | 施工前，两项记录都应已取得 |
| fault_kind | string，供策划核对的接点／外放故障类别 | contact_fault或speaker_fault；不生成故障答案菜单 |
| fault_confirmed | boolean，本段开始时是否已确认故障 | 前两件为false，需试修改善；第三段两件为true |
| trial_results | object，临时处理ID→结果 | 前两件各填两项；第三段为{}，直接处理已知故障 |
| trial_results.*.improves | boolean，该临时处理是否改善原有现象 | 选择工具还不算通过，点击试听后才记录结果 |
| trial_results.*.feedback_id | string，引用presentation.id | 无改善时重现原症状，有改善时给稳定输出反馈 |
| hints | 两个string，按顺序读取的主动求助提示 | 第一层提示该比较什么，第二层解释现象与处理的关系 |
| plans | array，本委托可以提出的正式方案 | 包含method_id、accepted、reason、requires_agreement和response |
| plans.accepted、reason | boolean与string，用途是否满足及拒绝原因 | 闹钟的耳机方案为false，原因是睡觉时不会戴耳机 |
| plans.requires_agreement | string或null，具体同意ID | 公共机耳机方案引用manual_notice_agreement |
| plans.response | string，施工成功后的顾客回应 | 被拒绝的方案使用reason，不播放施工成功回应 |
| methods.cost、result_state | object与string，消耗及物件结果 | headphones消耗work2/module0，物件变为headphones |
| methods.keeps、loses | string，施工前展示的功能变化 | 耳机方案保留收听，失去外放 |

玩家选择临时处理以后，工作台只显示试修状态。点击【试听】时，才显示并记录这次结果；重复试听不多扣工作格，也不发放模块。前两件各自至少有一次改善记录，才允许正式施工。已有一次改善后继续比较其他临时处理，不会抹去先前记录；正式施工仍按所选方案执行。

【谁来用】【怎样用】的回答按委托保存，切换物件后仍可回看。方案卡可以提前查看，但施工前必须已问清本件用途。玩家提出不合用方案时，顾客说明原因；同意尚未取得或资源不足时，也分别说明缺少哪项条件，资源保持原数。

提示通过玩家主动求助展开，第一层指向尚未比较的现象，第二层解释关系。两层提示都不扣资源，不代替玩家完成施工；程序只读取这两段预设文字。

### 2.3 表现字段怎样使用

| 字段 | 含义 | 谁提供、何时显示 |
|---|---|---|
| items.visual_key、shape_key | 物件画面语义键与共用轮廓 | 美术交接后由程序绑定；私人、公共机共用radio轮廓 |
| items.has_headphone_port | boolean，物件入场时是否自带耳机口 | 私人机为true，公共机为false；施工后的变化另存运行态 |
| presentation.visual_state | string，局部画面状态 | 如signal_flicker、contact_repaired、headphone_port_on_speaker_off |
| presentation.audio_key | string，对应声音语义键 | 如speaker_intermittent、speaker_stable、headphone_monitor |
| presentation.text | string，与声音和画面表达同一结果 | 每次反馈同时显示，关闭声音也能完成判断 |
| cases.initial_feedback_id | string，入场表现ID | 只显示已知现象，不提前显示未询问的用途 |
| methods.feedback_id、transfer.feedback_id | string，施工或转用后的表现ID | 扣除资源、保存结果后播放一次；之后可再次试听 |

当前资源键均为待接入名称，检查脚本只核对非空值和ID引用，不把它们当作已经存在的图片或音频文件。关键差异需要由画面与文字共同说明：声音恢复时，连接或输出指示也恢复；失去外放时，外放通路关闭、耳机口保留，文字直接写出这一变化。

### 2.4 段落与一次转用

| 字段 | 含义与限制 |
|---|---|
| chapters.id、case_ids | 段落和本段委托；每件委托只列入一段 |
| chapters.resources | 进入本段时设置的供给；s01为work1/module0，s02为work1/module1，s03为work3/module1 |
| must_complete、allow_replan | 前两段需完成教学委托；第三段可确认留下未处理委托，并提供重新安排 |
| agreements.id、case_id、owner_id | 同意ID、相关物件和作出决定的人 |
| request、reply、refused_reply | 协商内容、同意与拒绝的回应；只有同意后相应条件才成立 |
| transfer.chapter_id、source_case_id | 第三段开放；来源为第一段修好的私人收音机 |
| headphone_test_feedback_id | 先试听私人机耳机口，记录可正常收听后，才可取得转用同意 |
| agreement_id、cost、gain | 读取donor_transfer同意；消耗work1/module0，获得work0/module1 |
| result_state、feedback_id、limit | 私人机变为headphones，显示对应反馈；本段最多转用一次 |

阿程听见缺件后可以提出先试私人机耳机口。耳机测试不扣工作格，也不直接取得同意；玩家说明失去外放的后果以后，阿程才能同意或拒绝。取消施工、顾客拒绝以及未完成前置条件，都不扣资源。

相应施工或转用完成后，该次同意记录固定。玩家需要改变安排时，使用【重新安排】连同物件和资源一起恢复，不能只把同意改成拒绝。

两条完整安排的结果如下：

| 安排 | 顺序与资源变化（工作格／外放模块） | 结束后的物件与负担 |
|---|---|---|
| 保留私人机 | 起点3／1；闹钟更换后2／0；周姐同意人工转告，公共机改装后0／0 | 私人机保留外放；周姐使用耳机听写，再逐间转告 |
| 授权转用 | 起点3／1；免费耳机测试、阿程同意后转用，变为2／2；两件各更换一块，最后0／0 | 闹钟和公共机恢复外放；私人机只剩耳机收听 |

公共设备的集体收听限于晚间值班时段，阿程在家随时与孩子一起听的条件仍有变化。回访按实际结果分别说明物件去向和人物行动，不把公共收听写成全部损失已经消除。若有委托未处理，结尾列出它仍未解决的用途，不播放两件全修好的回应。

### 2.5 配置、运行状态与重新安排

配置保存上述规则和文字，不在游玩时修改。一局运行状态保存当前段落、工作格和模块、各委托已经问过的问题、临时处理草稿、试听记录、是否出现过改善、施工状态、物件状态、同意记录、私人机耳机测试和转用次数。界面当前选中的委托、提示层级与方案另外保存。

【开始修补】：当玩家点击此按钮时，先检查本件用途是否问清、前两段是否已有试修改善、方案是否合用、必要同意是否取得及资源是否足够。全部满足后，一次性扣除消耗，保存物件结果并标记委托完成，再播放反馈。再次点击已完成委托只查看结果，不重复扣除。

第三段开始时，先设置work3/module1，再保存完整起点，随后才允许询问和施工。【重新安排】恢复这一份起点，包括前段已经修好的私人收音机、第三段两件未完成委托、原有资源、本段询问与试修记录、顾客同意、耳机测试和转用次数；关闭当前方案预览，清空未提交的界面选择。供给不再叠加，回访与结尾也按恢复后的结果重新读取。

## 三、程序之间怎样交接

副程序A负责一局规则状态：询问记录、试修与试听、施工条件、资源和段落恢复。副程序B负责物件、文字、按钮与差分显示，并把玩家动作交给逻辑。主程序负责读取配置、主入口、场景接线、合并与完整包。

先交一件委托。主程序载入配置，副程序A能返回当前状态与处理结果，副程序B用占位资源完成真实点击，再增加余下委托。三名程序都有编程基础但Godot经验较少，先复用现有工程，不新增通用事件语言、自由文本识别或专用编辑器。

本版需要的动作只有：询问用途、选择临时处理、试听、请求提示、预览方案、记录人物同意、确认施工、试听私人机耳机、转用、结束段落和重新安排。响应带回成功与否、原因、当前状态和本次反馈ID，函数名由主程序按实现统一。

配置修改由策划提交，主程序先运行候选检查，再交给逻辑和界面。三者共用委托、物件和表现ID，避免按显示名称猜测对象。具体岗位工时沿用第三稿，每人最多24小时；新增表现和返修均计入本人额度。

## 四、美术先确定哪些事情

### 4.1 画面主次

默认先试低饱和的纸片插画：木柜台、灰绿远景与局部暖光保持统一，物件轮廓比背景细节更清楚。人物采用静态半身，身份通过姿态、衣服使用痕迹与携带物区分，表情变化只做确实需要的部分。

![三种画法对照](figures/美术方向对照.png)

左图的手绘纸感适合旧物叙事，但现有纹理仍偏细；中图的硬边套色容易控制数量与一致性；右图提供像素方向的参照，尚未通过统一像素网格检查。原图继续用于画法比较，图中物件不代表本版四件委托，三列也没有可直接接入的独立图层。

REPLACED的参考价值在空间层次。远景压低对比，工具和物件留在清楚的中景，门框或货架作为两侧前景。先用分层素材完成深度感，实时焦点、复杂灯光和角色逐帧动画不进入首版。

### 4.2 一件物品需要交什么

以收音机为例，美术B在同一画布上保留机壳、刻度、接点、外放模块和耳机接口等必要分层，交出基础图、临时连接、试听恢复、正式修好和耳机输出这些状态。各状态共用物件位置和主要轮廓，程序替换或显隐对应部分；临时接好的线与正式固定的线需要能区分。

私人、公共收音机共用结构，外壳、标签与原有接口不同。检测模块画在工具上，库存图标只代表正式替换用的外放模块，避免玩家误以为工具会补充库存。

美术A负责委托卡、两项询问、已知用途、试听记录、方案卡和确认状态。数字、文字和按钮保持原生文本。深色场景保留气氛，长文字使用稳定的阅读底色；未问到的用途不预先铺满界面。

参考窗口先沿用工程的1152×720。首次样例正文从22px左右开始，标题约30px，辅助说明尽量不低于18px；最终以实际运行尺寸检查。状态同时有文字或图形标记，颜色和声音都不单独承担判断信息。

源文件保留分层，导出PNG保留透明背景。使用Krita时，可用图层与蒙版分离物件和限制局部修改；生成的平面图需要拆分或重绘以后，才能按分层源稿交接。[Krita图层与蒙版](https://docs.krita.org/en/reference_manual/layers_and_masks.html)

### 4.3 先用一次样例校准制作速度

两位美术各留60—90分钟，使用已经熟悉的工具。美术A完成一张委托卡和方案按钮的基本状态；美术B完成一件中性旧物的基础图与一个试听前后变化。把两者放进同一画面，检查物件是否跳位、文字是否被纹理干扰、变化是否看得出。

随后由副程序B接入。修改一个源稿部件、重新导出，并在游戏里正确替换以后，再决定后续物件精度。若这一轮已经消耗过多时间，就减少纹理或改用硬边套色，复用这件物品继续检查。

## 五、给美术AI agent的固定资料

共同资料入口仍为[美术参考与提示词](../art-reference/README.md)。每次任务提供同一份说明、参考图、合格样例与本次修改范围；原有方向PNG和完整生成提示词保留原路径。当前方向图只用于比较，尚没有成员完成并认可的运行资源。

美术A可以把以下任务交给自己的agent：

```text
读取项目AGENTS.md、04的美术说明和planning/art-reference/README.md，检查本人分支与已有文件。完成一张中性委托卡：物件名、入场情境、谁来用和怎样用两个询问、询问后留下的用途记录、临时处理与试听、方案预览。按1152×720参考画面保留原生文字，提供默认、选中、不可施工及原因提示。用现有工具保存可编辑源稿，导出必要预览，再配合副程序B检查实际字号和状态。先完成这一张卡，记录实际耗时和交接位置。
```

## 六、接入前怎样检查

在工作副本根目录运行：

```powershell
node planning/proposals/fixtures/检查候选配置.mjs
```

脚本先检查字段、资源数量、ID与表现引用，再按配置推演以下处理：

| 检查内容 | 需要得到的结果 |
|---|---|
| 第一件先接检测模块，再临时处理接点 | 前者不改善，后者试听后改善；选择工具未试听时仍不能施工 |
| 临时处理、重复试听、用途询问与预览 | 资源保持不变，检测模块不会加入库存 |
| 第二件沿用两项试修 | 接点处理无改善，检测模块恢复铃声；询问完成后可换正式模块 |
| 用途未问全、闹钟耳机方案、周姐尚未同意 | 施工被拒绝，说明具体原因，状态与资源保持 |
| 私人机未试耳机、阿程拒绝或尚未同意 | 不能转用；测试本身免费，同意后也须确认转用才扣资源 |
| 最终两条完整安排 | 均为0格／0块，私人机状态与选用路线一致 |
| 重复施工、重复转用或资源不足 | 操作被拒绝，不再次扣除或发放资源 |
| 施工或转用后再改变同意 | 操作被拒绝，已执行的同意与物件状态保持一致 |
| 仅先修公共机并结束 | 闹钟作为未处理委托留下，允许收束 |
| 施工或结尾后重新安排 | 完整恢复第三段起点；私人机、询问、同意、耳机测试、转用与资源均无残留 |

数据通过以后，再由程序检查实际按钮与状态接线、美术检查试听前后的表现、策划检查解释与人物回应、独立测试检查输入和完整包。这些工作采用同一份配置，分别报告实际完成的部分。
