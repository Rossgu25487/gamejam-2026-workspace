# 加入团队与同步工作

用户已确定：自己的 Codex 每轮完成后保存、检查、单独提交并推送，保留必要恢复线索。以下分支与权限规则继续适用。

日常入口是[团队工作台](https://rossgu25487.github.io/gamejam-2026-workspace/)；具体操作见[使用指南](协作空间使用指南.md)。
[仓库](https://github.com/Rossgu25487/gamejam-2026-workspace)已公开，浏览和克隆无需邀请；向原仓库推送需要对应写入权限。

## 1. 取得自己的工作副本

需要协作者写权限时，向队长提供 GitHub 用户名与岗位，由 owner 在[访问管理](https://github.com/Rossgu25487/gamejam-2026-workspace/settings/access)邀请。接受状态以 GitHub 为准，不在文档维护动态名单。
注册、登录和验证由本人完成，不索取或公开凭据。没有写权限也可先 clone 并完成本地准备。

在本人选择的新独立目录中克隆：

```powershell
git clone https://github.com/Rossgu25487/gamejam-2026-workspace.git
cd gamejam-2026-workspace
```

从仓库根打开 Codex，读取 AGENTS.md、README.md、本人的 Issue 和岗位资料。核对主程序给出的 main 提交号、当前分支及未提交工作，不覆盖已有项目。
首次提交若缺少 Git 作者身份，在本地配置本人身份，优先使用 GitHub 的隐私提交信息；不把私人联系信息写进公开文档。

## 2. 独立分支与目录

常规成员各自电脑独立 clone，在已确认的 main 起点创建任务分支，例如：

```powershell
git switch -c codex/gameplay/counter-check main
```

同机多任务需要隔离时，从主工作副本根使用：

```powershell
./tools/start-role.ps1 -Role gameplay
```

Role 可选 planner、lead、gameplay、integration、ui_art、visual_art、qa、ops。新分支默认从本地 main 创建；需固定起点时用 `-BaseBranch` 指定已确认提交。
脚本返回 `.local/roles/<role>` 和 `codex/<role>/workspace`，在返回的 Path 重新打开 Codex/Godot；脚本不会切换当前任务目录。
已有 worktree 或角色分支保持原状态，不 reset、不覆盖、不自动更新。两人不得同时写同一目录。

## 3. 任务与成果怎样同步

1. 从网页进入本人 [GitHub Issue](https://github.com/Rossgu25487/gamejam-2026-workspace/issues)，确认负责人、需求依据和验收条件。Issues 是这些信息的唯一维护源。
2. 在自己的分支完成已授权修改与相称检查；将 PR、文件或运行包位置、版本、实测和未测项更新到对应 Issue。
3. 推送与 PR 沿当前授权执行，主程序统一接口与分支合并，保持 main 可运行。普通小改动无需额外逐项审批。
4. 验收满足且已有关闭授权时，在 Issue 关闭为完成；取消使用 Not planned。网页会按 GitHub 数据更新，不通过本地勾选制造全队状态。
5. handoff 只留 Issue 链接、本机分支/提交、未提交文件和恢复线索；不另抄任务状态、负责人、排期或验收表。

缺少 Issue 或推送权限时，先保留本地成果与可直接使用的更新摘要，交有权限者处理，不借用他人账号。
Git 不会同步被忽略的运行包或视频；Issue 中必须给接收者能实际取得的链接或交付方式。

## 4. 下一次接手或换岗

先读 Issue 的最新要求，再核对本机恢复线索。保留未提交工作后，在持有 main 的主工作副本中同步：

```powershell
git switch main
git pull --ff-only origin main
```

无法快进或有冲突时按实际差异处理，不强制覆盖。已有角色分支正常合入所需更新；再次运行 start-role 不等于更新分支。
策划依据需核对提交号、路径与 sha256；文件变化由 planner 确认后重指定，不能沿旧 revision 宣称内容未变。
换岗先在原 Issue 交接成果和未完成事项，更新实际负责人，再进入新岗位的独立目录与分支。旧 handoff 只留下恢复位置或指向新任务的链接。
GitHub 写权限属于仓库层级，目录归属是团队约定，详见[协作协议](协作协议.md)。

Godot 顶部“协作空间”仅提供网页、仓库、任务入口和本机版本提示；旧三页操作已退出日常入口。策划原件和当前依据按[策划说明](../planning/README.md)在文件中维护，再通过 Git 同步。

## 5. 每轮提交与意外恢复

开始任务时，Codex 记录当前提交和已有改动；完成时保存产物、执行必要检查，把本轮修改单独提交并推送。报告中提供结果提交号；有未完成、未测试或未推送内容时如实列出，不写成全部完成。

仓库文件的回退使用保留历史的撤销提交。先确认目标提交只包含需要撤销的内容，并保护当前工作，再执行相应操作：

```powershell
git show --stat <需要撤销的提交号>
git revert <需要撤销的提交号>
```

尖括号内容需替换为已核对的真实提交号，不直接照抄。出现冲突时逐项比较；不使用强制重置或强推覆盖队友工作。撤销提交检查后按当前分支规则推送或提交 PR。

GitHub 的任务正文、指派、标签与关闭状态独立于 Git。修改前在本机 `.local/recovery/` 保留涉及任务的原记录，修改后记录新任务编号及本轮结果。需要恢复时，先比较当前记录与本轮结果，只还原本轮涉及的字段；本轮新增且决定取消的任务用 Not planned 关闭，保留历史。

若已发布网页，仓库回退后重新发布需要恢复的页面；页面上的任务则按 GitHub 源记录单独恢复。浏览器错误或关闭编辑器不代表源文件丢失，先核对 Git、任务与本机恢复线索，再采取操作。
