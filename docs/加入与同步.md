# 加入团队与同步工作

仓库：[Rossgu25487/gamejam-2026-workspace](https://github.com/Rossgu25487/gamejam-2026-workspace)，当前为 public，可公开浏览和克隆。
向原仓库推送分支需要对应写入权限。协作者须接受邀请并使用本人账号认证；邀请与接受状态以 GitHub 为准，岗位文件和 Godot 按钮不会自动授予写入权限。

## 1. 获取协作者写入权限

需要向原仓库提交工作的成员向队长提供 **GitHub 用户名＋当前岗位**。岗位 ID 为：`planner`、`lead`、`gameplay`、`integration`、`ui_art`、`visual_art`、`qa`、`ops`；岗位可以经交接调整。

Owner 从 [仓库访问管理](https://github.com/Rossgu25487/gamejam-2026-workspace/settings/access) 邀请准确账号，沿已有授权执行。成员使用对应账号接受；发送邀请与接受邀请分别核验，不在本说明维护动态名单。
没有 GitHub 账号的成员需本人注册；账号登录、验证与凭据保管由本人完成，Codex 不代填，也不把凭据放进仓库。
尚未取得写入权限时仍可公开读取、克隆并完成本地准备，保留自己的提交与交接摘要；向原仓库推送前再确认权限。

## 2. 公开读取与独立克隆

1. 可直接打开公开仓库查看资料。HTTPS 克隆无需先接受协作者邀请，读取与写入分别确认。
2. 如需向原仓库推送，使用被邀请账号接受邀请并正常认证；访问管理中的实际状态为准。网络连接或认证失败按具体错误处理，不当作游戏代码故障。
3. 在本人电脑选一个独立目录，克隆仓库：

```powershell
git clone https://github.com/Rossgu25487/gamejam-2026-workspace.git
cd gamejam-2026-workspace
```

4. 从该仓库根打开 Codex，告知本人岗位；先读根 AGENTS.md、README.md、[岗位说明](../岗位工作流/00_分发与使用说明.md)和自己的交接记录。
5. 核对主程序公布的本轮 `main` 提交号。8 个岗位从同一已确认快照开始，后续依赖通过明确的新提交号交接，不凭“已经更新”判断版本。

首次提交若 Git 提示缺少作者身份，在本人本地仓库设置自己的 Git 提交身份，优先使用 GitHub 提供的隐私提交信息。不要沿用队长身份，也不把私人联系信息或登录凭据写入公开文档。

## 3. 启动角色工作目录

**常规情况：每人一台电脑、一个独立 clone。** 在已确认的本地 `main` 上创建本任务分支，例如：

```powershell
git switch -c codex/gameplay/counter-check main
```

将例子的 role 和任务名换成本人的实际分工。已有工作分支继续使用，先检查未提交改动，不为重新接手覆盖当前工作。

**同机多个任务，或需要额外隔离目录：** 从主工作副本的仓库根运行角色启动脚本，例如：

```powershell
./tools/start-role.ps1 -Role gameplay
```

`-Role` 接受 `planner|lead|gameplay|integration|ui_art|visual_art|qa|ops`。新角色分支默认从本地 `main` 创建；需要固定本轮共同起点时用 `-BaseBranch` 传入主程序已确认的 main 提交号。目录为 `.local/roles/<role>`，分支为 `codex/<role>/workspace`；在返回的目录根打开 Codex，再打开其中的 `game/project.godot`。
已有 worktree 时，脚本只验证归属并返回；角色分支已存在但未挂载时，会沿用该分支。两种情况都不 reset、不覆盖、不自动更新到最新 main。核对返回的 Commit，再从本人交接继续；同一 role 有并行任务时另外明确隔离目录和分支。
该工具只处理本机目录隔离，不处理 GitHub 邀请、远端权限或实时同步。不同角色即使在同机，也不得共用同一个可写目录。

**换岗时：**先在原岗位交接中留下当前提交、未完成工作、文件归属和接收人，再按明确的新分工进入新岗位的独立 clone 或 worktree，使用对应分支并重新打开 Codex/Godot。仅在面板里切换角色不会切换工作目录、接管未完成任务或扩大写入范围；每个岗位记录同一时段由一个明确负责人维护。

## 4. 本地工作怎样进入共同版本

1. 依据 `planning/current.json` 和当前需求版本工作，只改本人范围，更新 `workspace/handoffs/<role>.md`。任务引用工作分支/提交号、策划路径与 sha256；不同分支的 revision 不能当作全队线性版本号。
2. Godot“协作空间”保存到当前工作副本。策划原件、当前指针及交接文件需要正常提交，其他人才能取得；窗口中的保存成功只说明本机写入成功。
3. 做与改动相称的检查，提交本任务文件和自己的交接记录，推送本人分支并向 `main` 创建 PR。说明需求 ID/依据版本、改动、验证和待接入项。
4. 主程序统一接口与分支合并，核对直接受影响的生产者、消费者和版本，保持 `main` 可运行。常规已授权小改动直接完成和交接，无需逐次先审批；产品规则取舍由 planner 决定。
5. 合并后主程序记录新的 `main` 提交号和需要接手的内容。运行包按单独交包方式提供，Git 同步不会自动带上忽略的本地构建包。

PR、推送与合并沿当前仓库授权执行；缺权限时保留本地提交及交接依据，由有权限者接收，不借用他人账号或擅自绕过权限。

## 5. 下一位怎样同步

先确认本人未提交工作已妥善保留。在持有 `main` 的主工作副本中更新：

```powershell
git switch main
git pull --ff-only origin main
```

若 `main` 已在另一 worktree 打开，回到那个工作副本执行。命令提示冲突或无法快进时保留当前成果，按实际分支差异处理，不强制覆盖。
新任务从更新后的 main 开始；已有角色分支按正常合并方式接收所需更新，检查受影响点。重新运行 start-role 不等于更新工作分支。
恢复时核对本人依据与主程序集成 main 是否不同，保留当前改动后正常同步需要的更新。active 依据的原件哈希变化时，先由 planner 核对并重新指定，不沿旧 revision 宣称依据未变；不 reset 脏目录，也不增加每分支版本表。
下一位读取当前依据和上游交接，核对新提交号、接口、资源或包版本，再完成自己的接入。无需重新创建计数工程或重复全部准备。

## 6. 读取与协作就绪的判断

- 读取就绪：可以公开查看或克隆仓库，无需协作者邀请。
- 写入协作就绪：本人已接受邀请并具备实际写入权限，可按授权向原仓库推送自己的分支。
- 独立 clone 或 worktree 能从仓库根启动工作，角色与文件归属明确。
- 起始 main 提交号、当前依据和本人交接记录可读取。
- 本人环境实际运行情况已记录；未执行的 GUI、输入或跨机器检查继续保持未执行。

GitHub 协作者写入权限作用于仓库，目录归属属于团队分工约定，不提供岗位目录级权限隔离。实际操作还受 GitHub 权限和分支规则约束。
Godot 中选角色只改变工作入口；修改范围按已交接的岗位及[协作协议](协作协议.md)，接口按[接口与交接](接口与交接.md)。换岗不自动改变 GitHub 权限，点击按钮也不代表可以覆盖其他成员工作。
