# 接口与交接

依据版本：`prep-v1`。需求 ID：`PREP-001`。当前阶段：赛前准备（manifest 为 `preparation`，简称 `prep`）。
本合同定义中性计数夹具：初值 0、每次有效操作加 1、重置回到 0。它验证规则表达、程序接线、二维资源和测试交接，正式玩法待命题。

## 1. 实现位置与所有者

| 文件 | 所有者 | 职责 |
|---|---|---|
| `game/data/demo_config.tres` | planner | 练习数值：`initial_value`、`step` |
| `game/data/demo_config.gd` | lead | `DemoConfig` Resource 类型与字段定义 |
| `game/features/counter_demo/counter_model.gd` | gameplay | `CounterModel` RefCounted，唯一真实计数状态 |
| `game/ui/counter_view.gd`、`counter_view.tscn` | integration | `CounterView` Control，显示与用户操作信号 |
| `game/ui/theme.tres` | ui_art | 主题、颜色、字体与控件样式；不改交互脚本 |
| `game/main/main.gd`、`main.tscn` | lead | 加载配置、创建逻辑、连接界面与逻辑 |
| `game/art/ui/` | ui_art | UI 源文件与必要导出 |
| `game/art/visual/` | visual_art | 图标、背景、二维物件源文件与必要导出 |

已按本轮文件核对模型、界面、配置、主场景和主题位置。现有二维样例为 `game/art/visual/ambient_grid.svg`、`loop_mark.svg`，同时承担可编辑源文件与运行资源，当前界面引用这些位置。后续确需区分原生源稿和导出时再按需分子目录，不为分目录复制或移动现有资源。
这些路径应与工程和 [manifest](../workspace/manifest.json) 一致。首次接手须核对实际文件和类定义；发现缺失或差异时记录具体项并由 owner 补齐，不能把文档列出视为运行验证完成。

## 2. 程序合同

| 生产者 | 提供接口 | 消费者与用途 |
|---|---|---|
| DemoConfig | `initial_value`、`step` | 主程序读取，默认分别为 0、1 |
| CounterModel | `configure(initial, step)` | 主程序传入配置，建立初始状态和步长 |
| CounterModel | `read_value()` | 返回当前整数状态，读取不改变状态 |
| CounterModel | `increment() -> int` | 按当前步长增加状态、发信号，并返回新值 |
| CounterModel | `reset() -> int` | 恢复配置初值、发信号，并返回初值 |
| CounterModel | `value_changed(value: int)` | 主程序连接至界面显示 |
| CounterView | `increment_requested`、`reset_requested` | 主程序连接至逻辑操作 |
| CounterView | `show_value(value: int)` | 仅更新可见数值，不保存第二份真实计数 |
| CounterView | `set_connected(connected: bool)` | 主程序完成接线后更新连接状态；独立预览不伪装逻辑已接通 |
| CounterView | `set_step(step: int)` | 主程序按配置同步按钮文字和步长提示 |

当前主入口先 configure，再连接模型和界面信号，然后设置连接状态与步长提示，并用 `read_value()` 首次同步界面。后续通过信号同步，现有主入口不依赖 `increment/reset` 返回值。输入只保留一条生效路径，避免按钮与自测按键叠加计数；副程序 A 的独立检查入口不接管主场景。

更改配置后是否需要重新运行，以当前实际加载方式为准并在交接中说明，不承诺热更新。改变初值或步长时，测试按对应配置和需求版本调整预期；默认夹具仍为 0/+1/reset。

## 3. 策划到制作

当前正式依据由 [planning/current.json](../planning/current.json) 指向，不按文件修改时间、聊天先后或文件名里的“最终”自动挑选。
指针字段包括 `status`、`path`、`title`、`revision`、`updated_at`、`sha256`。pending 的 sha256 可为空；active 必须绑定当前文件的 SHA-256。交接引用工作分支/提交号、策划路径与 sha256，revision 只作为该分支的局部修订号。
文件内容与已记录哈希不一致时，标记该依据待核，由 planner 检查来源与变化后重新指定；不得沿旧 revision 继续宣称依据未变。无关准备继续推进。
每项需求至少有 ID、目标、操作、规则或数值、所需资源及可判断的验收；可用 [简版策划模板](../planning/简版策划模板.md)。
缺少预期时，只将相关项标待确认。制作成员不擅改原件或自行补成正式规则。

## 4. 美术到接入

美术在自己的岗位记录注明：需求与依据版本、源文件与导出路径、实际尺寸与显示尺寸、格式、透明背景、锚点、必要状态、替换方式、来源/许可及 AI 使用情况。
UI 布局由美术 A 给出可编辑参考，副程序 B 落到 `counter_view.tscn`；美术 A 只直接维护约定的主题文件和自己的资源。
美术 B 提供二维图形，不默认承担模型或三维场景。碰撞、点击区域、层级接入及资源引用由程序处理并实测。
来源不明的资源就地标待核，使用自有占位继续接线，避免阻塞其他交接。

## 5. 程序到测试

主程序交付版本号或提交号、目标平台、运行包位置、启动步骤、当前配置、已知限制。没有版本号时用唯一包名和校验值补充标识。
测试以实际包独立操作，记录通过、失败、未执行。仅构建成功、无界面检查通过或成员口头报告，均不能代替可见界面与交互验收。
失败记录包含版本、复现步骤、预期及依据、实际结果和必要证据。回归引用新旧版本，复测原问题与直接受影响点；无实际问题可以通过。

## 6. 材料到提交

运营准备与已验收版本对应的说明、截图、视频、素材及 AI 声明，记录缺项和位置。
队长负责平台上传、审核状态与活动投稿；主程序的交包、测试的通过和平台的审核通过分别确认。
运营只处理已分配且预算内的任务，不默认承担赛后无限期推广、维护或试玩拉新。

## 7. 变更写在哪里

各人只更新 `workspace/handoffs/<role>.md`，使用简短条目即可：
`工作分支/提交号｜起始 main 提交号｜需求 ID｜当前策划路径与 sha256｜涉及文件｜接口或资源变化｜已验证/未执行｜消费者｜接入顺序｜下一步`。

接口名、参数、信号或资源路径变化时，先说明生产者与消费者。兼容更改先供应后接入；不兼容更改由相关 owner 与主程序确定同批合入的版本。主程序统一分支合并，下一接收者按新 main 提交号同步；操作顺序见[加入与同步](加入与同步.md)。一般改动沿已有授权执行，无需新增审批环节。
