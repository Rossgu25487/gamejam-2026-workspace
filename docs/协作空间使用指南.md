# 团队工作台怎么用

[打开工作台](https://rossgu25487.github.io/gamejam-2026-workspace/)。页面集中显示任务、共同版本、节点及团队入口。

## 找自己的任务

在“我的岗位”选择岗位，再选择准备或制作阶段。勾选“本机记住岗位”后，下次从首页进入会沿用选择；打开别人给的筛选链接时，以链接为准。

取消“本机记住岗位”后，后续打开仍保持关闭；当前视图链接依然可以带入指定筛选。

“待处理”包含待做、进行中和待验收，也可以分别查看。进度数字与当前岗位、阶段、搜索范围一致；已取消任务不计入完成比例。“重置筛选”回到全部岗位和当前阶段。需要让别人看到同样的列表，可以复制当前视图链接。

橙色“待处理”和绿色“已完成”是两个独立入口，列表上方会注明正在查看的状态。全队进度按准备、制作分别统计；命题前的正式任务仍是职责占位，显示“尚未开工”。任务完成比例按条数计算，不直接换算成工时或成品完成度。

打开任务后，在 GitHub 查看要求、交付位置和验收记录。页面不直接改共享状态：

| 状态 | GitHub 中的操作 |
|---|---|
| 待做 | Issue 保持打开，无进行中或待验收标签 |
| 进行中 | 使用 `status:doing` |
| 待验收 | 使用 `status:review`，移除旧状态标签 |
| 已完成 | 验收完成并获得关闭授权后，按 completed 关闭 |
| 已取消 | 按 Not planned 关闭 |

用 `role:<岗位ID>` 标明岗位，Assignees 指派具体账号。任务卡优先显示显式指派；没有原生指派时，显示已确认的岗位负责人。新建任务写清目标、完成条件、交付位置和时间依赖。

## 版本与节点

“共同版本”来自远端 main，源码下载对应显示的提交。试玩包单独显示，尚未发布时不会把源码当成可运行包。本机有未完成修改时先保存，再核对和同步版本。

节点统一按北京时间显示，建议与截止分开标注。日期到达不会自动完成任务，具体完成情况以交付和验收记录为准。工时规则见[根 README](../README.md#当前阶段与时间)，节点维护在 `workspace/roadmap.json`。

## 团队与资料

成员按“有待处理任务”“当前无待处理”“当前未分配任务”分组，各自列出待做、进行中、待验收和已完成数量。名单随阶段切换，不受上方搜索或岗位筛选影响；“查看任务”按具体负责人筛选。未登记账号的岗位及无人负责的任务另列，不能当作已经完成。

账号链接打开成员主页，“岗位工作流”打开对应文件。实际仓库权限与待接受邀请由队长在“仓库权限管理”中查看。

资料入口只指向该共同版本中已有的公开内容。策划原件与当前依据按[策划资料说明](../planning/README.md)维护，本机草稿不会因为出现在本地目录就自动进入工作台。

## 提醒未完成成员

任务旁或成员卡中的“提醒”会打开评论草稿。核对后复制，再打开对应 GitHub 任务发表评论；只复制草稿不会发出通知。待验收任务的提醒用于确认验收进展。

自动提醒按任务独立截止时间，在提前 3 天和 24 小时进入提醒窗口。先在 Issue 正文填写带时区的截止时间，例如 `截止时间: 2026-10-17T20:00:00+08:00`。尚未确定日期的任务保留空缺，项目总截止不会自动套入个人任务。

自动发送需部署并启用工作流；页面会显示部署检查结果，实际运行记录在 GitHub。评论 @负责人后是否收到邮件，取决于成员自己的 GitHub 通知设置。配置及防重复规则见[任务提醒](任务提醒.md)。

## 同步与本地修改

打开页面会先显示快照，再尝试读取 GitHub。刷新失败时保留上次内容和原时间，可直接打开任务核对。任务进度只在 GitHub 维护，浏览器只保存岗位偏好与筛选条件。

Codex 完成本轮后先保存、检查并本地提交。推送、PR 更新和工作台发布均需用户对本次内容明确授权。

工程开发使用 Godot；顶部“协作空间”提供网页快捷入口与本机版本信息。[加入与同步](加入与同步.md)说明分支和恢复步骤，[协作协议](协作协议.md)说明文件分工。
