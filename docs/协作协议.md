# 协作协议

本仓库服务于 8 人 Game Jam 团队。当前阶段为赛前准备（manifest 中为 `preparation`，简称 `prep`），使用 Godot 4.7.2 Standard、Compatibility 渲染器，工程入口为 [game/project.godot](../game/project.godot)。当前计数夹具只验证协作，正式设计待命题。

## 1. 从各自的电脑进入

1. 按[加入与同步](加入与同步.md)接受邀请并独立 clone 仓库，从主程序公布的同一 `main` 提交号开始。在本人工作副本根打开 Codex，先读根 [AGENTS.md](../AGENTS.md)、[README.md](../README.md)和自己的[岗位文件](../岗位工作流/00_分发与使用说明.md)。
2. 根据本人明确角色选择岗位；角色不明时先确认，不用操作系统用户名或文件作者猜测。不得把岗位流程安装为全局 Skill。
3. 每次任务使用 `codex/<role>/<task>` 分支，例如 `codex/gameplay/counter-reset`；先检查当前分支和未提交修改。
4. 每个人使用独立工作目录。同机多任务可用 `tools/start-role.ps1 -Role <role>` 从已确认的 main 提交建 `.local/roles/<role>` 和 `codex/<role>/workspace`；已有 worktree 或角色分支保持原状态，核对脚本返回的 Commit，必要时正常同步，不 reset 或覆盖。该工具不提供远端权限或实时同步。
5. [私有仓库](https://github.com/Rossgu25487/gamejam-2026-workspace)已创建，clone URL 为 `https://github.com/Rossgu25487/gamejam-2026-workspace.git`。首版推送以根 README 的实际记录为准；其余 7 位成员名单待提供，尚未邀请。未取得访问权限时继续本地准备，记录具体缺项。

## 2. 角色与文件归属

| role ID | 人员职责 | 主要写入范围 |
|---|---|---|
| `planner` | 用户兼策划队长，明确规则、范围、取舍和验收 | `planning/`、`game/data/demo_config.tres` |
| `lead` | 主程序，公共工程、接线、集成和交包 | `game/main/`、`game/project.godot`、`game/data/demo_config.gd`、公共设置、插件、`workspace/manifest.json` |
| `gameplay` | 副程序 A，交互与状态逻辑 | `game/features/counter_demo/` |
| `integration` | 副程序 B，界面与资源接入 | `game/ui/`，其中 `theme.tres` 归 `ui_art` |
| `ui_art` | 美术 A，UI 布局方案与组件表现 | `game/art/ui/`、`game/ui/theme.tres` |
| `visual_art` | 美术 B，二维图形与视觉资源 | `game/art/visual/` |
| `qa` | 测试，独立验收与问题回归 | `qa/`、`game/tests/`，生产代码与资源保持只读 |
| `ops` | 运营，过程素材与提交材料 | `release/`，按实际材料需要分子目录，不承担默认上传权限 |

每人另外独占 `workspace/handoffs/<role>.md`。根级指令、公共脚本和共享配置的变更由队长与主程序明确归属；不让多个角色同时维护一份公共文件。

## 3. 本轮如何开始和结束

- 先核对当前阶段、本人角色、需求依据和已有修改。首次最多集中问 3 个关键缺项，同时推进不依赖答案的工作。
- 每项改动标明需求 ID 与依据版本。当前准备夹具使用 [PREP-001 / prep-v1](接口与交接.md)；正式制作使用策划指定的版本。
- 原件保存在 [planning/inbox](../planning/inbox/README.md)，只有 `planner` 明确设定后才进入 [planning/current.json](../planning/current.json) 的当前依据。导入原件不自动切换依据。
- 任务引用“工作分支/提交号＋当前策划路径＋sha256”，并注明需求 ID。`revision` 仅表示该分支内的指针修订，不能当作全队线性版本号。active 依据必须与文件哈希一致；原件内容变化时由 planner 核对后重新指定，不悄悄沿用旧 revision。
- 有缺项时在受影响位置标待核，继续其他内容。未核实的外部代码或素材暂不进入正式可用清单。
- 结束时更新自己的一份交接记录：依据、改动、验证、卡点、接收者、下一步。已有通过结果在内容和依赖未变化时复用。
- PR 或本地交接沿已有授权自主完成，不为每次提交增加审批。不得覆盖他人未完成工作、擅自强推或删除他人分支。
- `main` 保持能够运行。提交者先做与改动相称的检查并提交 PR，主程序统一接口与分支合并，核对直接影响后记录新的 main 提交号；下一位拉取并核对版本，不把每次小改动扩大成全量审核。
- 未获授权不自动向他人发消息；需要协调时先在岗位记录写出可直接转交的事项。

恢复时比较本人工作分支的当前依据与主程序集成 main 的依据和提交。存在相关变化时先保留本人的未完成工作，再正常同步需要的更新，复核直接受影响部分；不对脏目录执行 reset，也不另建每分支版本表。

## 4. 接口与共享文件变化

修改前写清生产者、消费者、涉及文件、是否影响已有调用及同步顺序。具体合同见 [接口与交接](接口与交接.md)。

兼容扩展可先由生产者实现，再让消费者接入。删改名称、参数或资源路径时，先明确双方对应版本，由主程序协调一起合入，避免 `main` 出现一半更新。已有授权且归属清楚的调整直接做；产品规则分歧交给策划队长，其他工作继续。

## 5. Godot 中的“协作空间”

“协作空间”用于查看当前依据、把策划原件导入 `planning/inbox/`、编辑本人的岗位交接。插件的启用方法以根 README 和实际工程为准，按钮不可用时可在对应目录完成同一项本地工作。

插件读写当前 clone 或 worktree 内的文件。保存后仍需按 Git 分支提交与同步，其他成员才会得到更新；界面显示的岗位不授予 GitHub 访问、修改他人文件或切换策划依据的权限。
