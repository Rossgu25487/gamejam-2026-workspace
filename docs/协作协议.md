已确定的个人分工：Rossgu25487 是本项目唯一策划，负责策划案输出与维护、剧情及对话文本，并承担部分测试。测试分工先按设计规则是否落实、剧情文本与触发是否正确、关键玩家流程和体验是否符合预期执行；具体测试用例在方案和运行版本明确后细化。qa 继续承担独立运行、环境与资源检查、操作问题复现及修复回归。策划需要的程序修复由对应程序处理，代码合并与交包由 lead 统筹。

这几项职责与队长协调、提交共用本人正式制作的 12 小时总预算。职责固定不等于具体内容已经开工，玩法、剧情题材和细排期待命题确认。
岗位可以经交接调整：在 Issue 明确接收人和未完成事项，保留原分支成果，再使用新角色的独立目录。GitHub 写权限作用于仓库，不按岗位目录隔离；分工仍需遵守。

## 3. 实现、合并与恢复

- 从本人独立 clone/worktree 和主程序明确的共同起点开始，使用 `codex/<role>/<task>`；接入步骤见[加入与同步](加入与同步.md)。
- 当前任务引用 Issue、需求 ID、策划路径/sha256 和分支/提交号。revision 只是该分支的局部计次，不能用作全队线性版本。
- 先给短计划，直接完成已授权、可逆的工作；最多集中询问 3 个关键缺项，不依赖答案的内容继续推进。
- 接口变化明确生产者、消费者和接入顺序；主程序统一合并，main 保持可运行。兼容扩展先供应后接入，不兼容更改明确同批版本。
- 验证与改动相称；将结果、成果位置与剩余问题更新到对应 Issue，不另建平行验收表或每日状态抄本。
- handoff 仅记录 Issue 链接、本机分支/提交、未提交文件、恢复命令或下一次本地操作。对全队有效的决定留在 Issue 或其引用的正式依据中。
- 恢复时先核对 Issue、当前依据与 main 的相关变化，保留工作后正常同步；不 reset 脏目录，不覆盖他人成果。
- 推送、PR、Issue 更新与外部发布按当前授权执行。没有权限时准备更新摘要，不自行发送普通聊天、邮件或邀请。

## 4. 策划与 Godot 的边界

planner 与 Codex 在 `planning/inbox/` 保存适合公开的原件，明确采用后更新 `planning/current.json` 的路径和实际哈希，再通过 Git 同步；详情见[策划说明](../planning/README.md)。
原件不原地改写，文件或指针发生变化时先比较再更新。未知来源只在受影响项待核，其他工作继续。
Godot“协作空间”只提供网页、仓库和任务快捷入口及本机版本；旧岗位长文、交接编辑、原件导入和设当前标签页已退出日常入口。
