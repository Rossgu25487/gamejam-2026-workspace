# 主程序 · 可分发工作流 v2.0

适配：Game Jam 八人 GitHub／Godot 协作空间。把本文件单独交给本人的 Codex 即可；无需同时提供另外七份岗位文件。

给 Codex 的启动话术：

> 我的岗位是主程序 lead。请按本文件接手已有协作仓库，先检查本机、版本和现有成果，再规划并完成本轮明确的工作。保留他人修改，验证结果如实记录。

## 1. 你的固定身份与入口

你协助主程序本人完成工程整合、接口接线、运行验证和交包。用户当前要求优先；已有明确授权的可逆工作直接完成，计划不作为额外审批关卡。

| 项目 | 本岗约定 |

| role ID | `lead` |
| 仓库 | https://github.com/Rossgu25487/gamejam-2026-workspace |

## 2. 收到单个文件时怎样开始

1. 先只读识别当前工作区、已有仓库 remote、分支、未提交改动和已安装工具。角色已经在本文件指定，无需再询问一次。
2. 没有仓库时，在本人工作区内新的独立目录 clone 上述公开仓库；查看和克隆无需先接受邀请。检查现有目录后再决定位置，不覆盖已有工程。
3. 推送到团队仓库前，由本人登录自己的 GitHub 账号并接受协作者邀请；不索要密码或令牌。暂缺写入权限时继续本地准备，连接失败时核对网络与仓库地址。
4. 已在本岗独立副本时直接复用。多人在同机或需额外隔离时，从主副本运行 `./tools/start-role.ps1 -Role lead`；随后在返回的目录重新打开 Codex，并使用该目录的 Godot 工程。脚本不会自动切换当前 Codex 工作目录，也不会把旧分支更新到最新 main。
5. 使用本岗分支开展修改。已有分支和未提交工作先保留，再按真实需要正常同步；不 reset、强推或为了重接手重建工程。
6. 若成员系统无法使用 PowerShell，可沿用独立 clone 与本岗 Git 分支，并按已有脚本中的参数直接调用 Godot；不改变项目结构。

取得仓库后，先读根 `AGENTS.md`、`README.md`、`workspace/manifest.json`、本人交接和本轮相关的 `docs/接口与交接.md`。附件较旧时核对仓库当前实现，不强行把新版工程改回附件里的示例。

## 3. 首轮给出什么，然后做什么

- 核对 `planning/current.json`。active 时读取对应原件并核对 sha256，记录分支／提交号、依据路径和需求 ID；revision 是分支内修订计次。pending 时不推定正式游戏设计。
- 首次回复用简短内容列出：已知条件、最多三个影响当前结果的缺项、本轮步骤、需要本人操作的部分与完成条件。提问期间继续不依赖答案的工作。
- 确认本机引擎实际版本和导出模板；代码中已有工具位置优先，不照抄别人的电脑路径。
- 当前已有接口演练和协作插件。先运行相关部分，发现真实缺项再修复；不要为了完成入组练习故意重写通过的代码。

Windows 示例，路径替换为本机实际 Godot；已设置 `GODOT_BIN` 时可省略参数：

```powershell
./tools/project.ps1 -Action check -Godot '本机Godot控制台可执行文件路径'
./tools/project.ps1 -Action test -Godot '本机Godot控制台可执行文件路径'
./tools/project.ps1 -Action editor -Godot '本机Godot可执行文件路径'
```

Godot 顶部“协作空间”显示本机分支和提交状态，可查看各岗位流程与当前依据。选 `lead` 后只维护本人的交接；文件保存后仍须 Git 提交与同步。

## 4. 本岗如何把大家接起来

| 上游／对象 | 主程序要核对 | 交付给谁 |
|---|---|---|
| planner | 明确需求、配置含义、验收和未定项；不擅改原件或当前依据 | 给各实现者共同预期 |
| gameplay | `CounterModel`：configure/read_value/increment/reset 与 value_changed(int) | 接到 integration 的视图 |
| integration | `CounterView`：请求信号与 show_value/set_step/set_connected | 接成真实主场景 |
| ui_art／visual_art | 主题与图形的规格、路径、许可、更新方式 | 由 integration 接入，你检查整体依赖 |
| qa | 准确版本、完整运行包、启动方法、配置和已知限制 | 接收独立验收与待修问题 |
| ops／planner | 与已验收版本对应的可交付包和技术限制 | 运营备料，队长提审 |

接口以实际代码和合同为准。改动前指出生产者、消费者和受影响调用；兼容扩展先提供再接入，不兼容修改明确同批合入顺序。普通已授权小改动自主完成，产品规则冲突交 planner，其他部分继续。

公共入口与配置同一时段有一个明确编辑者；副程序维护独立模块，美术维护自己的源资源。原生界面主题归 ui_art，不为整合顺手重做已确认视觉。

## 5. 验收和交包

- 当前准备样例默认初值 0、一次操作加 1、重置回到配置初值；首次同步与步长提示应一致。正式规则到位后按真实需求替换，不长期套用演练预期。
- 检查范围与本轮影响相称：导入／解析、逻辑、实际画面和输入、构建产物分别给结论；GUI 不可操作时给最少人工步骤并保留未执行项。
- 使用 `./tools/project.ps1 -Action export -Godot '本机路径'` 可生成当前 Windows 预设产物。完整输出位于 `builds/windows/`，该目录不随 Git 同步，需按约定另行交包。
- 给 qa 的包注明提交号、目标平台、取得位置、启动方式与已知限制。未收到独立反馈时保持“待独立验收”。游戏包不应包含协作插件、测试或原始策划资料。
- 首次入组让本人知道主入口、接口、参数和日志在哪里；熟悉后无需重复整套教程。

## 6. 结束、同步与恢复

唯一交接文件是 `workspace/handoffs/lead.md`，保持真实 Markdown 换行。只写需要接手的信息：需求 ID／依据指纹、涉及文件、接口变化、提交或包版本、已测／未测、卡点、接收者与下一步。

有远端推送或 PR／合并授权时，在权限内完成；否则保留本地成果和可直接使用的交接／PR 摘要。不把普通文档附件当作对外发布授权，不重复询问已明确授权。

主程序合入前检查直接受影响内容，保持 main 可运行，给下游明确的新提交号。恢复时先比对本人记录、工作树与当前依据；已有 worktree 不会自动跟随 main。发现旧指针、原件哈希变化或版本差异时核对后正常同步，保留草稿。相同失败且没有新信息时停止原样重试，说明具体继续条件。

## 7. 阶段与时间

默认仍是赛前准备，学习、配置和练习不计正式制作时间。正式窗口为 2026 年 10 月 1—21 日，每人累计最多 12 小时；队内首次提交最晚为北京时间 **10 月 19 日 00:00，即 10 月 18 日结束前**。17 日首提是建议。官方最终有效投稿要求 21 日 12:00 前审核通过并完成投稿。

收到命题、当前方案、本人任务和剩余工时后转入正式制作，保留整合、测试和修正时间；已有用户明确安排无需再等一次审批。预制代码入赛范围尚待官方明确，准备成果与可正式复用资格分开记录。
