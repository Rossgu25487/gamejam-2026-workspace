## 2. 首次接入：先看本机实际情况

公开仓库：`https://github.com/Rossgu25487/gamejam-2026-workspace.git`。
已有 Godot 4.7.2 Standard / Compatibility 工程 `game/project.godot`，原生“协作空间”和八岗位隔离脚本已提供；不要另建计数项目。

1. 先只读查看当前目录、已有资料、Git 仓库位置和工具能力，不覆盖现有文件。
2. 没有仓库时，确认一个新的独立目标目录后协助 clone；公开读取和克隆无需先接受邀请。
3. 向团队仓库推送修改前，由本人登录自己的 GitHub 账号并接受邀请；不要索取 token、密码或验证码。
4. 写入权限暂缺时继续本地准备。网络暂不可用时检查 Godot、目标系统、图形操作和证据工具，整理已有运行包与测试需求。
5. 已有仓库时核对 remote 是否对应上述地址、当前 branch/commit、未提交修改和本人目录；有差异先保留并说明，不自动 reset。
6. 从工作副本根依次读取 `AGENTS.md`、`README.md`、`workspace/manifest.json`、`planning/current.json`、`workspace/handoffs/qa.md`，再读本轮相关接口与运行说明。
7. 仓库的 `docs/接口与交接.md`、`docs/加入与同步.md` 可按需补读；单文件已给出的职责与规则可直接用于准备，不要求全读其他岗位。

## 3. 目录隔离与当前依据

- 不同电脑各自 clone；同机多任务使用独立 clone 或 worktree，任何两人都不共写同一个目录。
- 常规任务分支为 `codex/qa/<task>`；`codex/qa/workspace` 预留给角色启动脚本。
- 需要本机隔离时，从主工作副本根运行 `./tools/start-role.ps1 -Role qa`，核对输出的 Path、Branch、Commit 和本地修改状态。
- 在返回的 Path 重新打开 Codex，再打开其中的 `game/project.godot`。脚本不会切换当前 Codex 的目录，也不提供远端权限。
- 已有 worktree 或角色分支保持原工作，不自动更新到最新 main；先比较主程序指定的共同起点，再正常同步需要的更新，禁止覆盖脏目录。
- current 为 `pending` 时不推定正式游戏规则；本轮夹具引用 `PREP-001 / prep-v1`。
- current 为 `active` 时核对策划路径、文件 sha256、工作分支/提交号；revision 只表示该分支的局部修订，成员口头“更新了”不能代替核对。
- 哈希不一致或协作空间提示 stale 时，标明受影响依据待确认，暂缓相关通过结论，请 planner 核对后重新指定；你不修改原件或当前指针，其他独立准备继续。
- “协作空间”编辑的是本机文件；保存交接遇到磁盘冲突时保留草稿、重新读取并比较，不覆盖别人的更新。

## 5. 没有运行包时继续准备

1. 核对操作系统、Godot 与图形能力，记录哪些检查能亲自做、哪些需要人工协助。
2. 整理接收格式：包位置、版本或提交号、目标平台、启动方法、当前配置、已知限制和预期依据。
3. 在本人 handoff 写最小验证计划，先核对当前夹具规则与现有检查脚本，所有尚未执行项明确标记。
4. 有工程但无包时，可在当前授权内做静态或既有脚本检查；结果只覆盖相应范围，不记为运行包验收通过。
5. 向本人集中说明缺项和已完成内容，等待明确的新包信息后继续，不无限轮询、不虚构已到包。

## 6. 收到包后验证指定版本

记录准确的包名、目标平台、接收时间、提交号与本机环境；无唯一版本时补包校验值。先确认本次验收对象，避免误测旧包。
从约定位置取得实际产物并独立启动，不依赖原作者电脑中的编辑器、缓存或未交付资源。

| 检查 | 操作与依据 |
|---|---|
| 启动 | 进入约定界面，必要资源可见，能够执行操作 |
| 操作与重置 | 默认配置得到 0→1→2→3→0→1，一次有效操作只计一次 |
| 配置 | 核对 initial_value 与 step；参数变动时按该版本规则调整预期，不机械套默认值 |
| 资源 | 核对文字、按钮、图片、二维背景/物件的缺失、裁切、比例、层级及必要状态 |
| 重开 | 再次启动仍可运行；进度保留或清空遵循明确规则，未知只记录现象 |

规则缺少预期时标“待确认”，不猜测、不直接判作者错误；继续检查已明确部分。
检查结果必须区分：静态阅读、自动脚本、真实窗口点击/物理按键、截图查看、导出包启动、跨电脑独立运行。
headless 或脚本成功不证明物理输入与视觉；截图查看只证明所见画面，不证明操作链路。
没有 GUI、设备或必要工具时，给出最少人工步骤、预期与需回传证据，相应项目保持“未执行”。
人工代验注明执行者、版本和证据。搭建者此前的骨架测试可作参考，新成员在本人环境的接入仍需实际核验。

## 7. 问题与定向回归

- 分类为阻断、一般、建议：阻断影响启动或关键路径；一般违反已定要求但可继续；建议属于可选改善。
- 实际失败记录：问题 ID、版本/环境、步骤、预期及依据、实际结果、必要证据、对应负责人。
- 不确定根因就写现象；发现共享代码 Bug 也只交复现依据，不能借测试职责修生产工程。
- 无问题可以通过，不强求发现 Bug；未知预期、猜测和个人偏好不能充当失败证据。
- 收到修复先核对新旧版本、修复说明和影响范围，重走原步骤，再检查直接受影响部分。
- 仅因新变化、失败或具体疑点扩大验证，不默认全项目审计、全设备矩阵或重复所有旧检查。
- 证据只保留能复现问题的截图、短视频或日志；说明是已共享还是仅本机可见，不把忽略文件视作已随 Git 交付。

## 8. 交付、同步与恢复

只维护 `workspace/handoffs/qa.md`：本轮目标、分支/提交号、策划路径/sha256、需求 ID、包版本、实际结果、问题、卡点和下一步。
状态使用通过、失败、未执行。关键检查未执行时不得将整体验收写成通过；上轮搭建者通过与本人的实际通过分开。
当前任务已有推送/PR 授权时，完成相称检查后自主提交本人改动、推送角色分支并发起 PR，由 lead 统一接口与合并。
缺少对应授权时先交本地产物与可转交摘要。本 MD 不构成发布消息、联系队员、邀请账号或正式投稿的授权。
恢复时比较本人依据与集成 main 的变化，保留未完成工作后正常同步，只复核受影响部分；同因失败且无新信息时停止原样重试。
命题、当前方案、个人任务和余下工时明确后，再切换正式测试；日期到达不自动分配游戏内容。
