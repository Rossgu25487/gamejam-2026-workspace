# 八人岗位工作流 · 分发说明 v2.0

本版适配已经落地的 GitHub 私有仓库、Godot 协作空间和八个隔离岗位。原文件位置保持稳定，仓库界面与分发附件使用同一份内容。

## 1. 怎样发给队员

把对应岗位的一份 Markdown 发给该成员即可；每份都包含自己的仓库地址、固定角色、接入流程、文件归属、交接和完成条件，不要求成员先拿到全部附件。

| 成员 | 要发的文件 | 固定角色 |
|---|---|---|
| 主程序 | [01_主程序_工程与协作.md](01_主程序_工程与协作.md) | lead |
| 副程序 A | [02_副程序A_交互与逻辑.md](02_副程序A_交互与逻辑.md) | gameplay |
| 副程序 B | [03_副程序B_界面与资源接入.md](03_副程序B_界面与资源接入.md) | integration |
| 美术 A：UI 布局与组件 | [04_美术A_UI布局与组件.md](04_美术A_UI布局与组件.md) | ui_art |
| 美术 B：二维图形与视觉资源 | [05_美术B_二维图形与视觉资源.md](05_美术B_二维图形与视觉资源.md) | visual_art |
| 测试 | [06_测试_独立验收与问题回归.md](06_测试_独立验收与问题回归.md) | qa |
| 策划与队长 | [07_策划与队长_需求与决策.md](07_策划与队长_需求与决策.md) | planner |
| 运营 | [08_运营_记录与提交材料.md](08_运营_记录与提交材料.md) | ops |

两位美术都按 UI／二维能力安排。策划与队长为同一个人，合计八个岗位。

成员将文件上传给自己的 Codex，发送文件开头的启动话术，或直接说：

> 请完整阅读我提供的岗位工作流，按其中已明确的岗位协助我。先检查当前工作区、仓库和已有成果，再给出本轮小计划并完成能实际执行的准备；缺项集中说明，结果以实际检查为准。

无需复制为全局 AGENTS.md，也无需重新搭建项目。接入仓库后，由根 AGENTS.md 和当前资料提供实时上下文；附件中的示例若与后续已确认实现不同，先核对差异并采用当前要求。

## 2. 新成员第一次接入

- 仓库网页：https://github.com/Rossgu25487/gamejam-2026-workspace
- 克隆地址：`https://github.com/Rossgu25487/gamejam-2026-workspace.git`
- 项目技术基线：Godot 4.7.2 Standard／GDScript／Compatibility。
- 工程入口：各自副本中的 `game/project.godot`。

**仓库是私有的。**成员用自己的 GitHub 账号接受队长邀请；岗位文件不自动授予访问权限。GitHub 用户名与岗位名单由队长收齐，登录和验证由本人完成。

每个人各自电脑独立 clone、在本岗分支工作即可。同机多个 Codex 任务需隔离时，使用 `tools/start-role.ps1 -Role 本岗ID`；进入它返回的路径后重新打开 Codex 与 Godot。该脚本不会替当前任务切换目录，也不会重置旧工作区或自动更新到最新 main。

仓库已预留 `codex/<role>/workspace` 分支。具体任务可沿用合适的本岗分支或创建 `codex/<role>/<task>`，先核对版本和未提交工作，不直接覆盖 main 或其他岗位分支。

## 3. 这套文件会让 Codex 做什么

1. 识别本人的真实环境、仓库版本和已有工作，保留修改。
2. 读取本人岗位、交接与当前策划依据，只补与任务有关的资料。
3. 给出小步骤计划，已明确、可逆且获授权的本地工作直接执行。
4. 从现有工程接入，按自己的目录和接口完成验证或实际修改。
5. 将制作、接入、逻辑测试、画面、运行包和跨机器验证分别记录，未做项目保持未执行。
6. 更新本人的 `workspace/handoffs/<role>.md`，完成当前授权范围内的交接，保留明确恢复点。

本轮已有骨架通过的检查只是搭建时结果，不能代替队员在自己机器上的验证。准备的目标是能够进入、理解、使用和交接；已有内容通过时，无需为了显示进度故意修改它。

## 4. 共同接口与版本约定

- 设计依据由 `planning/current.json` 指向，记录路径和 sha256。导入原件到 `planning/inbox/` 不自动设为当前，具体选择由 planner 明确完成。
- 各项任务引用分支／提交号、需求 ID、策划路径和内容哈希。revision 是分支内计次，不用它单独判断跨分支新旧。
- 逻辑由 gameplay 提供，integration 接界面与两位美术，lead 整合，qa 独立验收，ops 配齐对应版本材料，planner 负责最终取舍与投稿。
- Godot“协作空间”的保存写入本机副本；其他人要通过 Git 同步才能取得。角色选择属于协作约定，GitHub 管理实际仓库访问。
- 已有副本恢复时先保留本地工作，按实际差异正常同步。遇到旧依据或外部修改提示，先核对后更新，不通过 reset、强推或绕过冲突提示处理。
- 普通小改动沿已有授权完成。远端推送、PR、正式发布与对外沟通按当前任务的具体授权执行，不因附件存在就扩大权限。

## 5. 阶段与工时

默认仍为命题前准备，学习、配置和练习不占正式制作的个人 12 小时。正式命题、方案和本人任务明确后继续使用本流程，不按日期自动开始做游戏。

正式窗口为 2026 年 10 月 1—21 日，每人累计最多 12 小时，包含本人承担的沟通、实现、验证和修正。队内首次提交最晚为北京时间 **10 月 19 日 00:00，即 10 月 18 日结束前**；17 日首次送审是建议。

官方最终有效投稿要求 10 月 21 日 12:00 前审核通过并完成活动投稿。当前演练不等于真实游戏；赛前预制代码能否正式复用仍需核清。完整赛事规则以[官方细则](https://www.taptap.cn/poster/NIKiDS1YShdA)为准。

## 6. 分发包与更新

仓库内 `岗位工作流/` 是八份文件的唯一维护源。`分发包/八人岗位工作流_v2.zip` 自动打包本说明和八份岗位 MD，共九份文件；不包含游戏源码、运行包、私人策划案或账号凭据。

修改源文件后运行 `./tools/package-workflows.ps1` 更新同一分发包。脚本检查角色、文件、版本与附件链接，并逐项核对 ZIP 与源文件内容一致。

工作流的组织参考 [OpenAI Docs：最佳实践](https://developers.openai.com/zh-Hans/guides/best-practices)，以目标、上下文、约束和完成条件支撑实际执行。在线源文件见[仓库岗位工作流目录](https://github.com/Rossgu25487/gamejam-2026-workspace/tree/main/岗位工作流)；具体协作资料在仓库根 README 和 `docs/` 下按需读取。
